# Diário de Bordo - Desenvolvimento PetConnect

Este arquivo serve para registrar as atividades, decisões e descobertas importantes durante o desenvolvimento.

**Data: 25/05/2024**

**Entrada por:** Marcelo (via Gemini)

**Resumo da Atividade:** Teste de ponta-a-ponta (E2E) dos controllers `UserController` e `PetController` e investigação da funcionalidade de upload de imagem.

**Detalhes Técnicos:**

1.  **UserController:**
    *   **GET /users & GET /users/{id}:** Testados e funcionando.
    *   **POST /users:** Testado e funcionando.
    *   **PUT /users/{id}:** Encontrado e corrigido um bug onde a validação impedia a atualização de um usuário existente. O endpoint agora funciona como esperado.
    *   **DELETE /users/{id}:** Testado e funcionando.
    *   **Conclusão:** O CRUD completo do `UserController` está validado e funcional.

2.  **PetController:**
    *   **Pré-requisito:** Um usuário "tutor" foi criado via API para obter um `tutorId` válido.
    *   **POST /pets, GET /pets, PUT /pets, DELETE /pets:** Todos os endpoints do CRUD foram testados e estão funcionando para a lógica de dados do pet.
    *   **Upload de Imagem (Descoberta Crítica):**
        *   Foi verificado que o endpoint `POST /pets` aceita um `MultipartFile`.
        *   A análise do código (`PetServiceImpl` e `FileStorageServiceImpl`) revelou que a implementação do armazenamento de arquivos é **simulada**.
        *   O sistema gera uma URL fictícia e a salva no banco de dados, mas não armazena fisicamente o arquivo. Isso é uma implementação de mock para desenvolvimento.
    *   **Conclusão:** O CRUD de dados do `PetController` está funcional. A funcionalidade de upload de imagem existe no código, mas usa uma implementação simulada que precisará ser substituída por uma solução real (ex: S3, armazenamento local).

3.  **AddressController:**
    *   Funcionalidade validada implicitamente através dos testes do `UserController`.

**Status Geral:**
*   Todos os endpoints planejados foram testados. A API está estável. Foi identificado que o upload de imagem é uma implementação de mock, o que é um ponto de atenção para a produção.

**Data: 24/05/2024**

**Entrada por:** Marcelo (via Gemini)

**Resumo da Atividade:** Investigação e implementação inicial do CRUD de Pet (Task KAN-3).

**Detalhes Técnicos (Baseado no `git diff` entre `KAN-2` e `feature/KAN-3-crud-pet`):**

1.  **Configuração:**
    *   Adicionada dependência de validação no `pom.xml`.
    *   Corrigida a porta do banco no `application.yml` para permitir a inicialização da API.
    *   Adicionado `application.properties` para o ambiente de teste.

2.  **Implementação da Feature `Pet`:**
    *   Criada a estrutura completa (Controller, Service, Repository, Model, DTO) para a funcionalidade de Pet.
    *   `PetController`: Criado o endpoint `POST /pets`.
    *   `PetService`: Iniciada a lógica de negócio, incluindo a preparação para o upload de imagem (requisito do Eduardo).

3.  **Depuração e Descobertas:**
    *   **Pré-requisito:** Para testar o `POST /pets`, foi necessário depurar o `POST /users`, que não funcionava.
    *   **Validações (Ponto do Bruno):** Durante os testes do `POST /users`, as validações de DTO se provaram robustas, retornando múltiplos `Bad Request` como esperado.
    *   **Dependência (Ponto do Andresson):** A ausência da autenticação foi contornada passando o `userId` manualmente.
    *   **Bug Crítico Encontrado:** O `POST /users` não retornava o `userId` na resposta, bloqueando a criação do pet. A causa foi identificada como uma divergência de nome de campo (`id` vs `userId`) entre a entidade `User` e o `UserDto`.
    *   **Status da Correção:** A análise do `git diff` confirmou que a correção no `UserDto.java` foi descoberta, mas ainda não foi commitada.

**Próximo Passo Imediato:**
*   Aplicar a correção no `UserDto.java` (renomear `userId` para `id`) e commitar, para então finalizar o fluxo de criação do Pet e destravar a task da carteirinha (ponto do Anthony).
